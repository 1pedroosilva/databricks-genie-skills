o que é

O que é uma skill

Uma skill é um arquivo de texto com uma regra dentro. O cabeçalho diz em que situações aquela regra vale, e em quais não vale. O corpo diz o que fazer quando a situação aparece. Um arquivo, um assunto.

Quem lê esses arquivos é o Genie Code, o assistente de programação do Databricks. Antes de responder, ele confere a tarefa contra o cabeçalho de cada arquivo disponível e carrega os que combinam, sem ninguém indicar qual usar.

Os arquivos existem em três níveis, e o nível define quem manda na regra.

plataforma

Skills que a Databricks mantém, iguais para todo mundo. Cobrem notebooks, Unity Catalog, dashboards, pipelines e MLflow.

workspace

Skills compartilhadas por um time em pasta comum. A regra vale para todos que trabalham naquele workspace.

usuário este projeto

Skills que moram no diretório pessoal e acompanham só quem as escreveu. Escolhi este nível para conseguir mudar uma regra sem depender de acordo com outras pessoas e sem afetar o trabalho de quem usa o mesmo workspace.

a lacuna

A lacuna que elas preenchem

As skills da plataforma ensinam o agente a operar as ferramentas do Databricks. Elas não dizem qual estratégia de gravação escolher, que nome dar a uma tabela, o que olhar numa revisão de código, nem em que pasta um arquivo novo deve nascer. Essas decisões são de engenharia, variam de time para time, e o agente resolve por conta própria quando ninguém escreve nada.

Quem decide qual skill entra em cada tarefa é uma linha só dentro do arquivo, a description. Ela lista as situações em que aquela skill deve ser acionada e as situações em que não deve. Escolha uma tarefa abaixo.

anatomia

Como uma skill é escrita

O arquivo tem duas partes. Um cabeçalho em YAML com nome e description, que é o que o agente lê para decidir se carrega. E o corpo em Markdown, que é o que ele lê depois de decidir que sim.

naming-conventions/SKILL.md
---
name: naming-conventions
description: Use ao definir, nomear, escolher, estabelecer ou criar
  nomes para assets NOVOS -- notebooks, tabelas, DataFrames, variaveis,
  pastas. Convencoes de numeracao (001_, 103_), principio DRY, padroes
  de caixa (snake_case, PascalCase). NAO use para revisar ou validar
  nomenclatura de codigo existente.
---

o trecho destacado é a fronteira negativa: sem ela, esta skill disputaria toda revisão de código com a code-review

Três critérios governam a escrita de todas elas.

Verbo de ação distinto

Cada skill responde por um verbo só: definir, criar, implementar, revisar, atualizar, commitar, decidir, organizar. Quando duas compartilham o mesmo verbo, as duas são acionadas na mesma tarefa e o agente carrega instrução demais.

Fronteira negativa explícita

Toda description declara o que a skill não faz, e para onde mandar quando o caso é de outra. É o que impede o agente de carregar meia dúzia de arquivos a cada pedido.

Especificidade máxima

A description precisa deixar claro quando acionar e quando não acionar. Se ela for vaga, a skill é carregada em qualquer pedido, inclusive nos que não têm nada a ver com ela.

processo

Como nasceram

Cada uma apareceu depois que o agente errou a mesma coisa duas vezes. Corrigir na conversa funcionava até o fim da sessão, e na sessão seguinte o erro voltava, porque nada tinha ficado escrito.

Elas começaram dentro do projeto da CVM, como instruções soltas para aquele pipeline. Em agosto ficou evidente que serviam para qualquer projeto e evoluíam em outro ritmo, e passaram a viver em repositório próprio.

O que eu publiquei antes de testar

No começo as skills não eram acionadas, e eu formulei três hipóteses sobre o que o sistema de acionamento exigiria: caracteres sem acento, fronteira negativa obrigatória e verbo imperativo em formato fixo.

Testei uma de cada vez, isolando a variável. As três foram refutadas: o acionamento aceita acento, entende intenção sem estrutura rígida e funciona sem a fronteira negativa. Os três critérios continuam valendo, mas como prática de clareza, não como exigência técnica.

Protocolo com os três testes isolados, evidências e tempos está em docs/protocolo_teste_empirico.md no repositório.

A avaliação

A avaliação existe porque eu não tinha como saber se as skills mudavam mesmo o resultado do trabalho, ou se o agente já fazia aquilo sozinho.

O desenho é o mesmo trabalho feito duas vezes, com os mesmos pedidos na mesma ordem, uma vez com as skills ativas e outra com elas desligadas.
